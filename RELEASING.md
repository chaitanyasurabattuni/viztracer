# Releasing VizTracer

A release is trustworthy when every artifact that will be published was
built from one source tree, installed into a fresh environment outside that
tree, and passed the full test suite there with no network access. This
document describes the local release gate that checks this on a macOS arm64
machine, the container commands for CI-like checks on Linux aarch64, and the
GitHub workflows that do the same on every platform before publishing.

## Prerequisites

The gate runs on a **macOS arm64** host and needs:

| Tool | Version | Notes |
| --- | --- | --- |
| Python | 3.9 or newer, any | Runs `tools/release_gate.py` itself, which uses only the standard library. On macOS `python3` works where these docs say `python`. |
| [uv](https://docs.astral.sh/uv/) | **0.11.2** exactly | Provides the pinned interpreters (3.12.13, 3.14.3, 3.14.3t) and builds the sdist and macOS wheels. The gate refuses other versions. |
| Docker | daemon running linux/arm64 natively | Docker Desktop on Apple Silicon. cibuildwheel and the Linux test containers use it. The output directory and the system temp directory must be shared with Docker (the defaults are). |
| curl | any | Downloads Perfetto's `trace_processor_shell`. |
| Network | during the build and prepare stages | PyPI, quay.io, Docker Hub, GitHub (python-build-standalone) and commondatastorage.googleapis.com (Perfetto). The test stages need no network. |

Everything else is pinned in the repository and installed by the gate:

* `tools/requirements/tools.txt`: cibuildwheel 4.2.1, twine 7.0.0, build 1.6.1 (and their dependencies), installed into a throwaway venv on uv's Python 3.12.13.
* `tools/requirements/build-backend.txt`: setuptools 84.0.0, the only build backend version used for the sdist and every wheel. The gate checks each wheel's `WHEEL` file to confirm it.
* `tools/requirements/test.txt`, `orjson.txt`, `trio.txt`: the test environments, all binary wheels.
* Test container base images, pinned by digest in `tools/release_gate.py`: `python:3.12-slim` and `python:3.14-slim`. cibuildwheel pins its manylinux2014 image by digest itself.

The requirement files were resolved with
`uv pip compile --universal --python-version 3.10 --exclude-newer 2026-10-01 tools/requirements/<name>.in`
(`tools.txt` with `--python-version 3.12`). To update them, re-run the same
command with a new `--exclude-newer` date, then run the gate.

uv is run with `UV_SYSTEM_CERTS=1` so it trusts the platform certificate
store. That is required behind TLS-inspecting proxies and harmless elsewhere.

## The gate command

From a fresh checkout:

```sh
python tools/release_gate.py --output-dir "/path/to/gate results"
```

`--output-dir` may contain spaces. It must be empty or absent. `--jobs N`
(default 3) sets how many Linux images are prepared and tested in parallel.
The exit status is 0 only if every stage passed. A full run took 7.5
minutes on an M-series laptop with warm caches (first runs also pull images and
interpreters).

Stages, in order (each writes `logs/NN-<stage>.log`):

| Stage | What it does |
| --- | --- |
| `preflight` | Checks the host is macOS arm64, uv is 0.11.2 and Docker runs arm64 natively. Records the git commit and whether the tree is dirty. |
| `export-source` | Copies the tracked and untracked-but-not-ignored files to a temporary directory. Nothing is ever built inside the checkout. |
| `tools` | Installs the pinned interpreters with uv and creates the tools venv. |
| `build-sdist` | `uv build --sdist` with the pinned setuptools. |
| `build-macos-cp312/cp314/cp314t` | `uv build --wheel` **from the sdist** with uv-managed 3.12.13, 3.14.3 and 3.14.3t. |
| `build-linux-cibuildwheel` | cibuildwheel 4.2.1 builds `cp312`, `cp314` and `cp314t` `manylinux_aarch64` wheels **from the sdist** in the pinned manylinux2014 image, natively on arm64 (no QEMU). Shared settings live in `[tool.cibuildwheel]` in `pyproject.toml`. |
| `check-artifacts` | `twine check --strict` on all seven artifacts. Checks there is exactly one sdist and the six expected wheels, that every file name and metadata version is the same, and that every wheel was generated by the pinned setuptools. |
| `download-trace-processor` | Downloads `trace_processor_shell` for mac-arm64 and linux-arm64 once, from the URLs in viztracer's own `web_dist/trace_processor` manifest, and verifies their sha256. |
| `prepare-macos-<tag>` | `tools/test_matrix.py prepare` in a temporary directory, with the matching uv interpreter (see below). |
| `prepare-linux-<tag>` | Builds a test image `FROM` the pinned `python:3.12-slim` / `python:3.14-slim`. For `cp314t`, uv 0.11.2 is pip-installed in the image and provisions CPython 3.14.3t. `tools/test_matrix.py prepare` runs inside `docker build`, the only point where these environments touch the network. |
| `test-macos-<tag>` | `tools/test_matrix.py run` against the prepared venvs. |
| `test-linux-<tag>` | `docker run --rm --network none <image> python /opt/vt/src/tools/test_matrix.py run ...`. |

Temporary directories, test images and containers are removed at the end,
whether the gate passes or fails (`results.json` → `cleanup`).

### What `tools/test_matrix.py` does

`prepare` (network allowed):

* Copies `tests/`, `example/json` and `.coveragerc` out of the source tree. The package itself is never copied, so the tests can only import the installed wheel.
* Creates one environment per optional-package combination, installs `tools/requirements/test.txt`, that combination's optional packages and the wheel:

  | Environment | orjson | trio | Runs |
  | --- | --- | --- | --- |
  | `full` | present | present | the full suite |
  | `orjson-only` | present | absent | tests marked `package_matrix` |
  | `trio-only` | absent | present | tests marked `package_matrix` |
  | `bare` | absent | absent | tests marked `package_matrix` |

  On free-threaded builds (`cp314t`) orjson publishes no wheels, and the suite declares no orjson matrix there, so only `full` (trio) and `bare` are prepared.
* Provisions `trace_processor_shell` into an isolated `HOME` (`.local/share/perfetto/prebuilts`, where viztracer's wrapper caches it), then checks the wrapper starts it with no `curl` on `PATH`.
* Writes `manifest.json` with the interpreter, each environment's packages and `pip freeze`, and the processor's sha256.

`run` (no network needed):

* Runs in each environment with that isolated `HOME`, the environment's scripts first on `PATH`, `PIP_NO_INDEX=1` and `UV_OFFLINE=1`. `VIZTRACER_TEST_PACKAGES` declares which optional packages must be present, and `tests/conftest.py` refuses to start if the environment disagrees, so a combination can never be silently skipped.
* Before running pytest, checks that `import viztracer` resolves inside the environment and has the wheel's version.
* Each run gets a fresh copy of the tests, a 30-minute timeout and its own process group. Nothing it starts outlives it.
* `--coverage` runs `COVERAGE_RUN=True coverage run --source viztracer --parallel-mode -m pytest` followed by `coverage combine`, exactly as CI does.

The tests themselves never install anything. `tests/package_env.py` only
describes the current environment and marks matrix tests with
`@pytest.mark.package_matrix`. Torch is not installed anywhere. Its tests skip
with "torch is not installed in this environment", and
`test_log_torch_without_torch` checks the error you get without it.

## Artifact layout

```
<output-dir>/
  results.json                  machine-readable summary (below)
  dist/                         the release set: 1 sdist + 6 wheels
    viztracer-1.1.1.tar.gz
    viztracer-1.1.1-cp312-cp312-macosx_11_0_arm64.whl
    viztracer-1.1.1-cp314-cp314-macosx_11_0_arm64.whl
    viztracer-1.1.1-cp314-cp314t-macosx_11_0_arm64.whl
    viztracer-1.1.1-cp312-cp312-manylinux2014_aarch64.manylinux_2_17_aarch64.whl
    viztracer-1.1.1-cp314-cp314-manylinux2014_aarch64.manylinux_2_17_aarch64.whl
    viztracer-1.1.1-cp314-cp314t-manylinux2014_aarch64.manylinux_2_17_aarch64.whl
  logs/NN-<stage>.log           full output of every stage, in execution order
  tests/<platform>-<tag>/       one directory per wheel (macos-arm64-cp312, linux-aarch64-cp314t, ...)
    <label>-<env>.log           pytest output of one run
    <label>-<env>.xml           JUnit XML of that run
    <label>-<env>.outcomes.json outcome of every test, for comparing runs
    summary-<label>.json        tools/test_matrix.py's summary for that wheel
```

`results.json` keys:

* `ok`: overall result. `failures`: why it is false.
* `source`: checkout path, git commit, dirty flag. `tools`: uv, Docker, cibuildwheel, twine and setuptools versions. `version`: the one version every artifact carries.
* `artifacts`: every file in `dist/` with kind, platform, python tag, size, sha256 and wheel generator.
* `environments`: one entry per wheel (`macos-arm64-cp312` ...) with the interpreter, the base image or uv interpreter, the trace processor provisioned, and each prepared environment's optional packages and `pip freeze`.
* `test_runs`: one entry per run with environment, packages, command, exit code, passed/failed/errors/skipped counts, duration, the `viztracer` module that was imported, and paths to its log, JUnit XML and outcomes.
* `stages`: name, status, duration, log and error of every stage. `cleanup`: what was removed.

## Container commands (Linux aarch64)

`tools/container_run.py` builds the same test image the gate builds from a
manylinux aarch64 wheel (for example one from `<output-dir>/dist`) and runs
the suite in fresh containers, always with `--network none`. It prints each
`docker run` command and records them in `<dir>/container-runs.json`.

```sh
W="<output-dir>/dist/viztracer-1.1.1-cp314-cp314-manylinux2014_aarch64.manylinux_2_17_aarch64.whl"

# Five consecutive plain runs on one CPU and 2 GB, each must finish in 15 minutes
python tools/container_run.py --wheel "$W" --output-dir out/plain --cpus 1 --memory 2g --repeat 5

# The same, the way CI measures coverage (coverage run ... -m pytest, then coverage combine)
python tools/container_run.py --wheel "$W" --output-dir out/coverage --cpus 1 --memory 2g --repeat 5 --coverage

# One run each with and without --cap-add SYS_PTRACE and --init; fails unless
# every test has the same outcome in all four
python tools/container_run.py --wheel "$W" --output-dir out/variants --variants
```

Each run is equivalent to:

```sh
docker run --rm --network none [--cpus=1 --memory=2g] [--cap-add SYS_PTRACE] [--init] \
  -v "$PWD/out/plain/plain-run1:/results" <test image> \
  python /opt/vt/src/tools/test_matrix.py run --root /opt/vt/root --results-dir /results --label plain-run1 --envs full \
  --chown "$(id -u):$(id -g)" [--coverage]
```

On Linux aarch64 the package ships no attach library, so in these containers:

* `tests/test_remote.py` tests that inject code skip with "VizTracer does not support attaching on Linux aarch64: no attach library is shipped for the aarch64 architecture". Signal-based `install()`/`--attach_installed` still run.
* `viztracer --attach PID` and `viztracer --uninstall PID` exit with status 1 immediately and print that message. `TestRemoteFail.test_unsupported_architecture` checks this in well under 10 seconds.

`vizviewer --use_external_processor` needs `trace_processor_shell`. The
`trace_processor` wrapper downloads it on first use. If it cannot be fetched
or started (offline, no curl, black-holed network, broken binary), vizviewer
now exits with status 1 and
`Error! Failed to start the external trace processor: ...` within about 20
seconds, instead of waiting forever. The test images have it provisioned, so
`test_use_external_processor` gets HTTP 200, and
`test_external_processor_fetch_fails`, `test_external_processor_fetch_hangs`
and `test_external_processor_cannot_start` check the failure paths with a fake
curl and a fake binary.

Observed on the development host (cp314 wheel, `python:3.14-slim`): five
consecutive plain runs at `--cpus=1 --memory=2g` took 122-131 s each and five
coverage runs 155-167 s each (245 passed, 13 skipped, every run). The four
`--variants` runs gave identical per-test outcomes.

## Reading a failed gate

1. The last lines of output (and `results.json` → `failures`) name the failing stage or wheel.
2. `results.json` → `stages` gives each stage's status and `error`. Open its `log`, which ends with the failing command's output and a traceback.
3. Common stage failures:
   * `preflight`: wrong uv version, Docker not running, or not an arm64 Mac.
   * `tools` / `build-*`: network or index problems (pip/uv output in the log), or a compiler error in `src/viztracer/modules`.
   * `check-artifacts`: `twine check` output, a version mismatch, or a wheel built by a different setuptools than `tools/requirements/build-backend.txt` pins.
   * `prepare-*`: a pinned requirement without a wheel for that interpreter (pip/uv says "no matching distribution"), or the trace processor download/checksum failing.
4. For `test-*` stages, look at `test_runs` entries with `"ok": false`:
   * `failures`/`errors` > 0: open the run's `log`. The pytest `-ra` summary is at the end, and `tests/cmdline_tmpl.py` logs the stdout/stderr of failing subprocesses. The JUnit XML has the same per test.
   * `timed_out: true`: the run hit the 30-minute limit and its process group was killed. The log shows the last test that started.
   * `import_check_ok: false`: the environment imported viztracer from somewhere other than the installed wheel, or with the wrong version.
   * `tests: 0`: pytest collected nothing, often a usage error such as a `VIZTRACER_TEST_PACKAGES` mismatch from `tests/conftest.py`.
5. To reproduce a Linux failure interactively, rebuild the image with `tools/container_run.py --keep-image ...` and `docker run -it --network none <image> bash`. The prepared environments are in `/opt/vt/root/envs`.

## GitHub workflows

* **`build`** (`python-package.yml`): on pushes, pull requests, daily and on `workflow_call`. Each leg builds a wheel with the pinned setuptools, runs `tools/test_matrix.py prepare` and then `run`. Legs cover Linux x86_64 (`ubuntu-24.04`), Linux aarch64 (`ubuntu-24.04-arm`), macOS arm64/x86_64 and Windows x64/arm64, for 3.10-3.14t. **`tests passed`** is the single fan-in job to mark as required. It fails unless every leg passed. The `coverage` job measures coverage and uploads it to Codecov. It and every Codecov upload are `continue-on-error` with `fail_ci_if_error: false`, so neither a coverage problem nor a missing `CODECOV_TOKEN` (forks) can fail anything.
* **`wheels`** (`wheels.yml`): builds one sdist and checks it with twine, then builds every wheel from it with cibuildwheel on native runners. Linux aarch64 uses `ubuntu-24.04-arm`, with no QEMU. Every wheel is tested by `test-wheels` (one job per OS and interpreter) with the same `test_matrix.py`, and each passing job records the wheel's sha256. The **`wheels tested`** job fails unless every build and test job passed. It then runs `tools/check_dist.py verify --tested`, which rejects any wheel without a passing test record for the same sha256, and uploads the `dist` artifact.
* **`release`** (`release.yml`): on a published GitHub release, runs `build` and `wheels` in the same workflow run. `publish` needs both, downloads that run's `dist` artifact, checks its version matches the release tag, and publishes it with `pypa/gh-action-pypi-publish` using PyPI trusted publishing (`id-token: write`, environment `pypi`, no password). Nothing is `continue-on-error`. Before the first release, add a trusted publisher on PyPI for this repository, workflow `release.yml` and environment `pypi`.

None of the workflows need repository secrets to run their test and build jobs. On a fork without secrets, everything except the PyPI upload itself works.

## Root causes behind the failing pipeline

Evidence was gathered in `python:3.14-slim` containers on this host with
`--cpus=1 --memory=2g --network none`, looping the affected scripts and
dumping every process's Python stack with `pystack` when a run hung.

1. **The Linux suite never finished: `vizviewer --use_external_processor` waited forever.**
   With no network, or no `curl` (true of `python:*-slim`), the wrapper's download fails and the process exits. `ExternalProcessorProcess._wait_start` kept calling `readline()` on the closed stderr pipe, which returns `""` forever, and `tests/test_viewer.py`'s `_wait_until_stdout_ready` looped the same way. faulthandler showed the suite stuck in `test_use_external_processor` after 200 s.
   Fix: `src/viztracer/viewer.py` first runs the wrapper with `--version` under a 20-second deadline, killing the whole process group so a hanging `curl` cannot hold it open. It then treats EOF from the server as an error and drains the processor's log afterwards. The test helper fails on EOF instead of looping. The processor is now provisioned before the test phase.

2. **`test_multiprocessing_pool` (and other pool users) hung: SIGTERM was swallowed by a fork hook.**
   `Pool.terminate()` takes `inqueue._rlock` and never releases it, then sends SIGTERM to workers. A worker forked while the pool was still starting runs viztracer's `os.register_at_fork` hook (`HookManager._after_fork`), which installs the SIGTERM handler and then starts the tracer. A SIGTERM arriving during that hook raised `SystemExit` inside it. CPython reports exceptions from at-fork callbacks as "Exception ignored" and continues, so the worker survived the SIGTERM and blocked forever on the lock in `get()`, and the parent waited forever in `p.join()`.
   Evidence: before the fix, 8 of 914 plain (no coverage) runs of the test's pool script (`file_pool`, forkserver workers on 3.14) hung. In every hang the surviving worker's stack was `pool.worker -> get() -> _semlock.__enter__` while the parent sat in `_terminate_pool -> p.join()`. In the 4 hangs where the run's stderr was captured, it contained `Exception ignored in atfork callback <bound method HookManager._after_fork ...> ... viztracer.py ... term_handler ... SystemExit: 0`. A 15-line script (`os.register_at_fork` hook + SIGTERM handler raising `SystemExit`) shows CPython discarding the exception and the child running on. With the fix: 0 hangs in 500 runs of the same script (and 0 in 300 runs of the spawn-pool script).
   Fix: viztracer's two SIGTERM handlers share `exit_on_sigterm()` (`src/viztracer/util.py`). When the signal lands inside the fork hook, nothing has been traced yet, so it takes SIGTERM's default action (terminate) instead of raising an exception that would be discarded.

3. **`test_multiprocessing_pool_with_pickle` and `test_multiprocessing_pool` hung under coverage: coverage.py's sys.monitoring core deadlocks with Python signal handlers.**
   On Python 3.14 coverage defaults to its `sysmon` core. `SysMonitor.start()`/`stop()` and its `PY_START` callback all take one non-reentrant `threading.Lock`. In a pool worker run under `coverage run --concurrency=multiprocessing` with `.coveragerc`'s `patch = subprocess`, the worker stops one collector and resumes the outer one: `start()` holds the lock across `sys.monitoring.restart_events()`. A SIGTERM from `Pool.terminate()` arriving then runs the Python handler, whose first frame fires `PY_START`, which blocks on the lock the same thread holds. On 3.14 the worker's trace is saved at interpreter exit, after coverage stops, so viztracer's handler is legitimately still installed at that point.
   Evidence: `pystack` showed `coverage/multiproc.py _bootstrap -> cov.stop() -> collector.resume() -> sysmon.start() -> restart_events() -> viztracer term_handler -> sysmon_py_start -> with self.lock` in every hung worker: 4 of 60 baseline runs of the pickle script, and 32 of 284 and 2 of 299 runs of the pickle and plain pool scripts with fix 2 but the default core. The same deadlock reproduces **without viztracer**: a spawn pool whose initializer installs `signal.signal(SIGTERM, lambda *a: sys.exit(0))` hung 15/150 times under coverage with `patch = subprocess` and 1/150 without it. With `core = ctrace` the same script hung 0/450 times, and viztracer's pool scripts 0/600 under coverage.
   Fix: `.coveragerc` sets `core = ctrace` (coverage's C tracer, available on 3.10-3.14t, including free-threaded builds). It has no such lock. This is a coverage.py bug, and the setting can be removed once coverage's sysmon core is safe against signal handlers.

4. **Hidden failures from `GITHUB_ACTIONS`-only test paths.**
   The package matrix only ran on CI, where it pip-installed packages mid-run. Its trio leg had been failing on Python 3.14, because `asyncio.get_event_loop()` no longer creates a loop there (`RuntimeError: There is no current event loop`). `file_log_async_with_trio` now uses `asyncio.new_event_loop()`. The matrix now runs everywhere, in prepared environments.

5. **Python console scripts at long paths were not traced.**
   When the interpreter path exceeds the kernel's shebang limit, installers (uv at ~127 bytes, pip/distlib at longer lengths) write a `#!/bin/sh` trampoline (`'''exec' '/long/path/bin/python' "$0" "$@"`). `is_python_entry()` in `src/viztracer/patch.py` only read the shebang line, so `subprocess` calls to such scripts ran untraced. The release gate exposed this: `test_python_entries` failed (1 traced process instead of 2) in all three macOS environments, which live under the long macOS temp directory. The trampoline's target is now recognized. `test_python_entry_sh_trampoline` fails on the old wheel and passes on the new one.

6. **SIGINT-based tests hung when the suite inherited an ignored SIGINT.**
   A gate run started as a shell background job (`cmd &`) hung in `test_report_server_devnull_stdin`. A native stack showed the report server parked in `kevent`, and a second SIGINT also had no effect. POSIX shells start background jobs with SIGINT ignored, `SIG_IGN` survives `exec`, and Python does not install its `KeyboardInterrupt` handler when SIGINT starts out ignored. So every subprocess the tests stop with SIGINT (report server, vizviewer, `--attach`) ignored it. `tests/conftest.py` now restores the default handler when SIGINT is ignored, so children start with the default disposition. Verified by running the viewer and report-server tests inside a background job: they hung before the fix and passed after it. The gate's 30-minute per-run timeout killed the hung run and reported it, as designed.

7. **Attach on Linux aarch64.** No `attach_linux_*.so` exists for aarch64, so `--attach` failed in gdb and the four injection tests failed. They now skip with the platform reason, and the CLI refuses up front (see above).

Also removed: the `flaky` retry helper (`tests/util.py`), the
`except Exception` that swallowed `test_multiprocessing_pool` failures under
`COVERAGE_RUN`, and every `GITHUB_ACTIONS` branch in the tests. The
CI-only waits and timeouts took their non-CI values (`test_trace_and_save`
20 s). The child lifetime in `test_regression.py`'s wait-for-child scripts is
3 s everywhere: that sleep keeps the child alive while the parent exits, and
is not a timeout.
